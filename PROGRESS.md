# Urgences Québec — intégration HA temps d'attente aux urgences

**Statut :** préface/design uniquement, aucun code écrit. Décidé en session Claude Code le 2026-09-24.

## Objectif

Intégration HA affichant le temps d'attente et le taux d'occupation des urgences du Québec, à partir des données ouvertes officielles du MSSS (pas de web scraping). Idée déclenchée par une insatisfaction avec une solution "maison" existante mal ficelée pour le même besoin.

## Source de données — vérifiée directement (2026-09-24)

- **Fichier CSV officiel MSSS**, licence CC-BY, via [Données Québec](https://www.donneesquebec.ca/recherche/dataset/fichier-horaire-des-donnees-de-la-situation-a-l-urgence) :
  - https://www.msss.gouv.qc.ca/professionnels/statistiques/documents/urgences/Releve_horaire_urgences_7jours.csv
  - https://www.msss.gouv.qc.ca/professionnels/statistiques/documents/urgences/Releve_horaire_urgences_7jours_nbpers.csv (celui qu'on veut — contient DMS/temps d'attente)
- **Téléchargé et inspecté directement** (pas juste la doc) : **120 installations uniques** (le chiffre "137" d'un résumé de fetch initial était faux — corrigé après téléchargement réel et parsing, confirmé 2 fois indépendamment).
- **Colonnes confirmées** : `RSS`, `Region`, `Nom_etablissement`, `Nom_installation`, `No_permis_installation`, `Nombre_de_civieres_fonctionnelles`, `Nombre_de_civieres_occupees`, `Nombre_de_patients_sur_civiere_plus_de_24_heures`, `Nombre_de_patients_sur_civiere_plus_de_48_heures`, `Nombre_total_de_patients_presents_a_lurgence`, `Nombre_total_de_patients_en_attente_de_PEC`, `DMS_sur_civiere`, `DMS_ambulatoire`, `DMS_sur_civiere_horaire`, `DMS_ambulatoire_horaire`, `Heure_de_l'extraction_(image)`, `Mise_a_jour`.
- **Important — le fichier est un snapshot courant, pas un historique** : malgré le nom "7jours", une seule ligne par installation avec un seul horodatage `Mise_a_jour` a été observée (2026-09-24T22:45). L'intégration doit construire son propre historique via le recorder HA — pas de backfill possible depuis la source.
- **`Mise_a_jour` est intégré aux données elles-mêmes** — pas besoin de deviner la cadence de rafraîchissement du gouvernement, l'intégration compare cet horodatage à chaque poll et ne considère une "vraie" mise à jour que si la valeur a changé.
- **Cadence annoncée** : horaire (page Données Québec), **pas encore confirmée empiriquement sur plusieurs heures consécutives** — un seul relevé vérifié jusqu'à maintenant.
- **Stratégie de poll retenue** (décidée 2026-09-24) : démarrer avec un intervalle raisonnable (15 min) et comparer `Mise_a_jour` à chaque sondage — les données ne sont traitées comme "nouvelles" que si cette valeur a changé (sinon skip, pas de bruit inutile dans le recorder/historique HA). En parallèle, logger les horodatages `Mise_a_jour` observés sur plusieurs jours réels pour découvrir le vrai pattern de publication (probablement horaire à un pic fixe, ex. `:45`), puis ajuster l'intervalle de poll une fois le pattern confirmé empiriquement plutôt que de le figer par hypothèse.
- **Coordonnées officielles trouvées — géocodage abandonné** (2026-09-24) : le fichier des urgences lui-même n'a pas de lat/long, mais le jeu de données [Fichiers cartographiques M02 des installations et établissements](https://www.donneesquebec.ca/recherche/dataset/fichiers-cartographiques-m02-des-installations-et-etablissements) (Données Québec, CSV disponible en plus du shapefile) contient `LATITUDE`/`LONGITUDE` officielles + adresse complète (`ADRESSE`, `CODE_POSTA`, `MUN_NOM`) pour **toutes** les installations du réseau (1589 lignes), clé `INSTAL_COD`. Jonction vérifiée avec `No_permis_installation` du fichier urgences : **120/120 (100%) de correspondance**.
  - **Tentative Nominatim/OSM abandonnée** : premier essai à 62% de succès fiable seulement — beaucoup de "succès" apparents étaient en fait le siège administratif du CISSS/CIUSSS régional (plusieurs installations réellement distantes de centaines de km, ex. Sept-Îles/Fermont/Port-Cartier/Forestville, regroupées sur une seule coordonnée identique). Remplacé entièrement par la jonction M02 ci-dessus — coordonnées officielles exactes, 120/120, aucune dépendance à un service de géocodage tiers au runtime ni même en one-time.
  - Script final : `tools/build_installations_geo.py` → `data/installations_geo.json` (bundlé avec l'intégration).
  - **Piège encodage trouvé en cours de route** : le fichier urgences MSSS est en **ISO-8859-1**, pas UTF-8 malgré les caractères accentués (confirmé via `file -i`) — bug qui existait aussi dans `coordinator.py` (corrigé le même jour, aurait planté au premier vrai fetch sur une instance HA). Le fichier M02 est en UTF-8 avec BOM (`utf-8-sig`).

## Design fonctionnel (décidé collaborativement)

- **Localisation** : `selector.location` natif HA — carte avec épingle par défaut sur la position HA (`hass.config.latitude/longitude`), déplaçable pour une position personnalisée.
- **Reconfigurable en tout temps** : Config Flow (setup initial) + **Options Flow** séparé — l'utilisateur peut revenir dans Paramètres → Appareils et services → Configurer pour changer la position, la région, le nombre d'hôpitaux affichés, etc., sans retirer/réinstaller l'intégration.
- **Tri par proximité** : distance calculée localement (haversine) depuis la position choisie ; option "afficher les N installations les plus proches" (nombre configurable).
- **Filtre par région** : liste déroulante dérivée directement du champ `Region` du CSV (pas de liste codée en dur).
- **Entités par installation sélectionnée** :
  - Temps d'attente (proxy : `DMS_sur_civiere` / `DMS_ambulatoire` selon disponibilité)
  - Taux d'occupation (civières occupées / fonctionnelles)
  - Patients 24h+ / 48h+ sur civière
  - Attributs : région, distance (si géoloc active)
- **Sensor dédié "Dernière mise à jour des données"** (device_class: timestamp) au niveau de l'appareil — visible clairement dans l'UI ("il y a X minutes"), pas caché en attribut.
- **Dashboard optionnel** : généré automatiquement (activable/désactivable au config flow), cartes triées par proximité, icônes mdi (hôpital/ambulance/horloge), code couleur selon occupation, carte horodatage bien visible.
- **Branding** : l'utilisateur a explicitement demandé un vrai logo pour l'intégration, pas une icône par défaut/carré vide — prévoir soumission au dépôt [home-assistant/brands](https://github.com/home-assistant/brands) (icon.png + logo.png, format/dimensions requis par ce dépôt) avant ou au moment de la publication publique, pas juste un `icon:` mdi générique dans le manifest.

## Dashboard optionnel — décision d'architecture (2026-09-25)

Exigence utilisateur : strictement optionnel via la config (`CONF_SHOW_DASHBOARD`, déjà présent dans l'options flow), robuste et fonctionnel pour n'importe qui installerait cette intégration publiquement (pas juste pour cette instance).

**Deux approches explorées et rejetées :**
1. *Génération manuelle via MCP (Claude)* — rejetée par l'utilisateur, à juste titre : ne fonctionne que parce que Claude a un accès MCP à CETTE instance précise. Un vrai utilisateur public n'aurait jamais ce mécanisme. Pas une vraie fonctionnalité partageable.
2. *Dashboard Lovelace auto-généré en Python* — recherché (`hass-lovelace_codegen` sur GitHub), confirmé que même cette librairie dépend de `homeassistant.components.lovelace._register_panel`, une fonction **privée** (underscore = API non garantie stable par HA). Librairie elle-même à peine maintenue (4 commits, 0 étoile). Rejeté : dépendance fragile sur une API interne, mauvais choix pour une intégration publique destinée à survivre aux mises à jour HA.

**Solution retenue : panneau custom (pas un dashboard Lovelace au sens strict)**, même mécanisme que le projet `config_map` de l'utilisateur (déjà déployé et fonctionnel) :
- `panel_custom.async_register_panel` — API **publique et stable** de HA, pas privée. Confirmé fonctionnel via `config_map`.
- Le panneau (`frontend/urgences-quebec-panel.js`, vanilla JS, aucune dépendance externe même si l'utilisateur a Mushroom/card-mod installés — pour rester portable pour n'importe qui) lit les entités en direct via `config/entity_registry/list` + `config/device_registry/list` (WS), groupe par appareil, calcule 3 tris (temps d'attente / occupation / patients 24h+, boutons d'onglet), grille de cartes avec code couleur (vert/jaune/rouge selon seuils par métrique), pleine page, `grid-template-columns: auto-fill` pour minimiser le défilement.
- `__init__.py` enregistre/retire le panneau automatiquement selon `entry.options[CONF_SHOW_DASHBOARD]`, réévalué à chaque setup/reload (déjà déclenché par la sauvegarde de l'options flow) — **aucune étape manuelle pour l'utilisateur**, contrairement à l'alternative "Lovelace Strategy" un temps envisagée (qui aurait demandé à chaque utilisateur de créer manuellement un dashboard).
- `require_admin=False` — données en lecture seule, accessible à tous les utilisateurs du foyer, pas seulement les admins.
- Cache-busting automatique du JS via hash MD5 dans l'URL (même fix que `config_map` avait dû découvrir après un bug de cache navigateur 31 jours).

**Pas encore fait pour cette partie** : déployé mais pas encore testé en conditions réelles dans le navigateur (aucune installation n'était sélectionnée dans la config au moment de l'écriture — voir plus haut).
